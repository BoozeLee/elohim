Three were routed to Jev as a single batched judgment call. It returned three

**Jev judges; it cannot act.** It cannot push, it cannot move a tag that
GitHub refuses to move through any API (`GH013`), and it cannot stop another
agent session. Routing an action to it produces a verdict about that action,
not the action. Anything below that Jev escalated is argued explicitly.

### Escalated 1 — push both repos now? Split it.

The viewer's leak fix is the only time-sensitive item: the live Pages site is
currently serving a screenshot containing the author's real home directory and
username. That tree is clean, its gates are green, and the push is non-force.
The elohim push carries no urgency at all and shares a repository with an
agent that is mid-edit. So: push the viewer, hold elohim.

A non-force push of already-committed paths cannot corrupt the concurrent
session's uncommitted work, so holding elohim is not about safety of the push
mechanically. It is about not interleaving two writers on one `main` while one
of them is mid-file.

### Escalated 2 — move the tag, or record the orphan?

Record it. Stating the fact satisfies the release without needing a browser,
and matches this project's own standard: a claim nobody re-derives is not a
fact, but neither is a fact nobody can check. Moving the tag remains worth
doing if a resolvable predecessor is wanted for `v0.2.0`; that is a
Settings-UI action only the user can take.

### Escalated 3 — is the missing Rust CI a real gap?

Yes, and not a release blocker. Nothing compiles `src-tauri` on any push, so
the 23 tests are hand-run and recorded nowhere a reader can check. That is the
same defect class as the unreleased commits: an unverified claim. It gets its
own commit rather than blocking the release.

### Not a judgment call

"Is another session active?" was sent to Jev and came back at 0.38 confidence.
It does not need a judgment model. `elohim_gate/mutation.py` carries 68
uncommitted insertions; a dirty file is the evidence. Observed directly.

## Gate before publishing

Phase 2.6 stops short of tagging and publishing, deliberately. The `v0.1.0`
tag is orphaned and cannot be moved without a human in a browser, so
publishing `v0.2.0` means shipping a release whose predecessor does not
resolve against the same history. That is a real trade, it is the trade the
roadmap names, and it is not one to close silently.

Publishing requires all of:

1. `python3 -m pytest tests/ -q` green, `check_text.py` green,
   `sync_adapters.py --check` green, on the exact tree being tagged.
2. `HEAD` unchanged across the gate run, so the gates describe the tree that
   ships.
3. An explicit instruction to publish, with the orphan stated in it.

## Gates for this repo

Run before every commit, from the root of this repository:

```sh
python3 -m pytest tests/ -q
python3 tools/check_text.py
python3 tools/sync_adapters.py --check
```

For the viewer:

```sh
cd src-tauri && cargo test
cd .. && env PAGES=1 npm run build
```

## Standing constraints

- Never rewrite published history or force-push a shared branch without
  explicit instruction.
- Never push without explicit go-ahead. Phase 0.1 is the one push this plan
  performs, and it is authorised.
- Nothing to elohim until the concurrent session stops. Every elohim commit
  in Phases 1 and 2 is written under that assumption and must be re-verified
  against a fresh `git status` immediately before committing, because the
  other session has moved `HEAD` four times during this work already.
