**Jev judges; it cannot act.** It cannot push, it cannot move a tag that
GitHub refuses to move through any API (`GH013`), and it cannot stop another
agent session. Routing an action to it produces a verdict about that action,
not the action. Anything below that Jev escalated is argued explicitly.

### Escalated 1 — push both repos now? Split it.

The viewer's leak fix is the only time-sensitive item: the live Pages site is
currently serving a screenshot containing the author's real home directory and
username. That tree is clean, its gates are green, and the push is non-force.
The elohim push carries no urgency at all and shares a repository with an
agent that is mid-edit. So: push the viewer, hold elohim.

A non-force push of already-committed paths cannot corrupt the concurrent
session's uncommitted work, so holding elohim is not about safety of the push
mechanically. It is about not interleaving two writers on one `main` while one
of them is mid-file.

### Escalated 2 — move the tag, or record the orphan?

Record it. Stating the fact satisfies the release without needing a browser,
and matches this project's own standard: a claim nobody re-derives is not a
fact, but neither is a fact nobody can check. Moving the tag remains worth
doing if a resolvable predecessor is wanted for `v0.2.0`; that is a
Settings-UI action only the user can take.

### Escalated 3 — is the missing Rust CI a real gap?

Yes, and not a release blocker. Nothing compiles `src-tauri` on any push, so
the 23 tests are hand-run and recorded nowhere a reader can check. That is the
same defect class as the unreleased commits: an unverified claim. It gets its
own commit rather than blocking the release.

### Not a judgment call

"Is another session active?" was sent to Jev and came back at 0.38 confidence.
It does not need a judgment model. `elohim_gate/mutation.py` carries 68
uncommitted insertions; a dirty file is the evidence. Observed directly.

## The defect was in this plan, not in the roadmap

This section originally read the other way round: that `docs/ROADMAP.md` was
wrong because the orphaned `v0.1.0` tag "now resolves to `69526efd`", making
the recorded `6231e88` stale. **It was not wrong.** `69526efd` is the **tag
object**; the roadmap names the **commit**, and
`git rev-parse 'v0.1.0^{commit}'` is `6231e8876b290ace67752eab10bec17fad10d819`.
Both readings are true of different things. I compared a tag object id against
a commit id, called the difference a moved tag, and wrote the correction up as
if the roadmap had drifted.

So the roadmap was right, this plan was the defect, and Phase 1.1 rewrote
rather than patched — which is the branch its own guard line asks for when the
premise fails. What actually changed in the roadmap is that the annotated-tag
fact is now written down: anyone who runs `git rev-parse v0.1.0` gets
`69526efd` and would otherwise conclude the document was stale. The recorded
commit was never in doubt and still is not.

The narrow lesson, kept because the plan is the document most likely to be
re-read as if it were current: a number that differs from a recorded number is
a question about *which thing* was measured, not evidence that something moved.

**2.3 was narrowed on purpose, so the tick is not a straight yes.** The report
page, `pages.yml`, the viewer's leak fix and the `glib` advisory are the
*viewer's* work, and recording them in elohim's changelog would imply elohim
shipped them. They are in `elohim-gate-viewer/CHANGELOG.md` (Phase 3.1), and
elohim's changelog says so rather than staying silent about them. elohim's own
CI unit suite is covered here, under the CI-and-gates group.

Two decisions in 2.1 worth keeping. Entries carry **no commit shas** — the
standing refusal is that a living document pins nothing that a rebase can
invalidate — so each group ends in a count that sums to a measured total, and
the real check is `git log afb61a3..main --format=%s`: any subject no entry

`afb61a3..HEAD` "as HEAD stood when this file was written, one commit before
the commit that wrote it", because a release's own commit escapes its own
table. A pinned number here would be wrong on arrival.

## Phase 3 — findings that should not wait for the release

- [x] **3.1** `elohim-gate-viewer/CHANGELOG.md`. The repo shipped a report
      page, a Pages workflow, two test suites and a leak fix with no release
      record at all. A release with no record of the release is the failure
      mode, not the exception.
- [x] **3.2** A Rust-only CI job for the viewer. The Pages workflow cannot
      carry it because Tauri's Linux dependencies break a plain
      `ubuntu-latest` runner, so the job installs the GTK/WebKit packages and
      then runs `cargo test` — testing the logic without building the Tauri
      bundle. Nothing else in this plan makes `src-tauri` verifiable on a
      push.
- [x] **3.3** Carry `glib` 0.18.5 `RUSTSEC-2024-0429` into the release notes.
      Not fixable within Tauri 2 — the fix needs `glib` 0.20, which arrives
      with Tauri 3 — and no viewer code references `glib` or any `Variant`
      type. Unreached is not the same as fixed, and the difference should land
      where a release is read rather than in a README nobody re-reads.

**3.1 needed one fact this plan did not anticipate:** the viewer has never been
tagged at all (`git tag -l` is empty, `git describe` fails), so there is no
orphan problem here at all. Its `[0.1.0]` heading therefore carries no date and
no release event, and the file has no comparison links, because there is
nothing to compare against.

**3.2 found a defect in its own first draft before it was committed.** The
ignored-count step ran `cargo` from the repository root, where there is no
`Cargo.toml`; cargo walked up and picked up a *different* workspace three
directories away and built three crates unrelated to this repo — rc=101. Both
cargo steps now pass `--manifest-path src-tauri/Cargo.toml`, so no deletion of a
YAML key can point them at another crate. `src-tauri/Cargo.toml` declares its
own `[workspace]`, which stops the ancestor absorbing this crate; it does not
stop a bare `cargo` from the root being absorbed, which is the half that bit.

The job's `Status` comment, and the changelog, both say plainly what is and is
not verified: the cargo steps were run by hand (23 passed, 0 failed, 1 ignored),
and **the `apt` step has never executed on a runner**. Eight package names taken
verbatim from Tauri's own prerequisites page is a citation, not a test. Swapping
an unverified claim for a differently-unverified one is the failure this project
exists to catch.

## Where the phases ended

All four phases are committed. Nothing is tagged and nothing is published, in
either repo — `git tag -l` is empty in the viewer and `v0.2.0` does not exist
in elohim, so the changelog heading `[0.2.0] — 2026-10-03` is a declaration and
not a release event.

Both trees carry commits that are not on their remotes, because Phase 0.1 is the
only push this plan authorises:

```sh
git rev-list --left-right --count origin/main...main   # in each repo
```

**No result is written here.** An earlier draft of this section did write one —
`0 4` in each repo — and it was wrong the moment the commit containing it
existed, because that commit is itself one of the unpushed ones. Two commits
from here the same argument retires: a figure recorded next to the command
that produces it is read as a fact, and this one cannot survive its own
transaction. Run the command. `CHANGELOG.md` takes the same shape for the same
reason, and so does the ROADMAP, which had one status line go stale three times
from rebases before it was rewritten to carry counts and commands instead.

One phase found a leak that the phases before it had introduced. Phase 1
committed this very plan file into a public repository with two lines naming the
author's home directory in it. The leak grep caught it; nothing else did. The
fix is in, and the sibling repo had already spent two commits on the same class
of accident, so the lesson is recorded in both changelogs. The obvious
follow-up — promoting that grep to a standing gate beside `check_text.py` — is
deliberately **not** done, because a release entry that quietly grows the
toolchain is the move this repository refuses.

## Gate before publishing

Phase 2.6 stops short of tagging and publishing, deliberately. The `v0.1.0`
tag is orphaned and cannot be moved without a human in a browser, so
publishing `v0.2.0` means shipping a release whose predecessor does not
resolve against the same history. That is a real trade, it is the trade the
roadmap names, and it is not one to close silently.

Publishing requires all of:

1. `python3 -m pytest tests/ -q` green, `check_text.py` green,
   `sync_adapters.py --check` green, on the exact tree being tagged.
2. `HEAD` unchanged across the gate run, so the gates describe the tree that
   ships.
3. An explicit instruction to publish, with the orphan stated in it.

## Gates for this repo

Run before every commit, from the root of this repository:

```sh
python3 -m pytest tests/ -q
python3 tools/check_text.py
python3 tools/sync_adapters.py --check
```

For the viewer:

```sh
cd src-tauri && cargo test
cd .. && env PAGES=1 npm run build
```

## Standing constraints

- Never rewrite published history or force-push a shared branch without
  explicit instruction.
- Never push without explicit go-ahead. Phase 0.1 is the one push this plan
  performs, and it is authorised.
- Nothing to elohim until the concurrent session stops. Every elohim commit
  in Phases 1 and 2 is written under that assumption and must be re-verified
  against a fresh `git status` immediately before committing, because the
  other session has moved `HEAD` four times during this work already.

The last clause turned out to be load-bearing rather than decorative. Each
elohim commit in Phases 1 and 2 was preceded by a fresh `git status`, and at
each of those four points the session was verifiably idle: `main` clean, and
`origin/main` level with it. Phase 1 landed at `0 1` and Phase 2 at `0 1`
carried forward, so nothing in this plan was written into a tree another writer
held open. The session is not assumed idle now — re-measure before the next
elohim commit rather than trusting this paragraph.
